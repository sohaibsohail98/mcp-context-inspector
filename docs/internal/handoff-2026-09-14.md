## Environment the next agent has

- Read/write access to this repo, on branch `terraform/import-prod-infra`.
- GitHub API access: can read PR status, CI runs and logs, push commits that
  trigger CI, comment on PRs. It does NOT have admin scope, so the branch
  protection API returns `403 Resource not accessible by integration`.
- **No usable GCP credentials.** `CLOUDSDK_AUTH_ACCESS_TOKEN` may be set in the
  environment but it is not accepted by the GCP APIs. Cannot run `gcloud`,
  cannot run `terraform plan` or `apply` against real state.
- `registry.terraform.io` is blocked by the network policy, so `terraform init`,
  `validate` and `providers lock` cannot run locally either. `terraform fmt
  -check -recursive` DOES work offline and does parse the HCL, so it catches
  syntax errors. Everything else is CI's job.
- The working loop is therefore: edit `.tf`, run `terraform fmt -check`, push,
  read CI's real plan output, iterate. `deploy.yml` applies on merge to `main`
  via Workload Identity Federation, so no human runs `terraform apply` by hand.
- What DOES need a human: merging a PR, setting branch protection, GCP Console
  click-throughs, and one `gcloud iam roles update` described below.

## Decisions made autonomously, worth knowing before a demo

These were judgement calls, not instructions, and each is one revert away.

- **`deploy.yml`'s rollback could have taken production down from a failing unit
  test.** It was guarded by a bare `if: failure()`, which fires when ANY earlier
  step failed, not just the smoke test. On a run where pytest or the image build
  failed, the "Record the currently-live image tag" step never produced an
  output, so the rollback would have run `terraform apply -var="image_tag="` and
  pointed Cloud Run at an unresolvable image. Now scoped to
  `steps.smoke-test.outcome == 'failure'` with an empty-tag guard at both ends.
  This is the single most interview-worthy thing in the branch.

- **The pinned `fix-verify` revision in `cloud_run.tf` was removed.** It pinned
  `mcp-context-inspector-00036-jev` by name at 0% traffic, imported as-is from
  manual debugging. Pinning a revision by name makes every future apply depend
  on that revision still existing, so the first Cloud Run garbage collection
  breaks the deploy for a tag nothing routes to. Removing it moves no production
  traffic, it only drops the `fix-verify` preview URL. If you want it back for
  the demo, revert that hunk of `c392e77`.

- **`tests.yml` used to fire twice per PR push**, once for `push` and once for
  `pull_request`, racing two `terraform-plan` jobs for the same tfstate lock.
  `push` is now scoped to `main`, with a per-ref concurrency group on
  `tests.yml` and a `deploy-production` group on `deploy.yml` that queues rather
  than cancels a half-written apply.

- **The IAM design is unchanged in shape**: resource-scoped writer and admin
  roles for what `github-deploy` actually manages, plus one custom role
  `deployTerraformReader` holding only reads. An earlier revision used
  `roles/resourcemanager.projectIamAdmin`, a full project-takeover vector, to
  fix a read-only refresh error. Do not re-add a broad predefined role to close
  a permission gap. Add the exact permission the 403 names to the custom role,
  and remember step 1: that change does not take effect on the PR that makes it.
